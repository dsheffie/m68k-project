    What the PLA proofs find: worked examples¶

    The 68k core does not run 68k instructions directly. Its front end decodes each instruction and expands it into a short flow: a sequence of micro-ops from the core's own instruction set (uisa). Most instructions get their flow from a table (the PLA). pla/prove_pla takes one 68k instruction and asks an SMT solver (Bitwuzla, with the terms built in z3) whether its flow does exactly what Boyer and Yu's MC68020 specification says. The question covers every possible value of the 16 registers, the condition codes and memory, not a sample of inputs.

    A proof compares the whole visible result:

    • d0-d7 and a0-a7;
    • the pc, including where a jump goes;
    • the condition codes X N Z V C;
    • every memory byte outside the instruction itself.

    The answer is one of:

    • PROVED;
    • CEX, a counterexample: an input on which the two disagree;
    • TIMEOUT;
    • NOTCMP, when there is nothing to compare: an illegal encoding, or an instruction outside the specification.

    A sweep over every flow where A7 is both an operand and moved by the instruction found two bugs: UNLK A7, and JSR through A7. The sweep covered 35,511 instructions: A7 in either addressing mode, A7 as an index register, and LINK, UNLK, PEA, JSR, BSR and RTS. Everything else in it proved or was not comparable, including:

    • LINK A7;
    • PEA (A7) and PEA d16(A7);
    • MOVE between A7 addressing modes;
    • every indexed form.

    Both bugs went unnoticed through millions of randomly generated test instructions. Each is described below, followed by two passing proofs.

    Bug 1: UNLK A7¶

    The instruction. UNLK An (opword 4E58+n) tears down a stack frame. The stack pointer gets An, then An is reloaded from the top of the stack, popping it. For UNLK A7 (opword 4E5F) the register being reloaded is the stack pointer.

    What the specification says. Yu's definition:

    (defn unlk-ins (an s)
  (let ((sp (read-an (l) an s)))
    (if (long-readp sp (mc-mem s))
        (write-an (l)
                  (long-read sp (mc-mem s))
                  an
                  (write-sp (add (l) sp (lsz)) s))
      (halt (read-signal) s))))

    The stack pointer is set to An + 4 first. Then An is written with the long at the old An. For A7, the long read from memory is written last, so it is the final A7. A reference simulator of the 68040 does the same.

    The flow, before the fix.

    add    a7, a7, x0       ; SP <- An
ld.32  a7, 0(a7)        ; An <- (SP)
addi   a7, a7, 4        ; SP <- SP + 4

    This order is right for every other An, but for A7 the + 4 runs after the load and lands on top of the loaded value.

    The counterexample. The solver can pick any inputs, or we can pin them with -p to get a readable one:

    $ prove_pla -v -p a7=0x2000 -p m32@0x2000=0x3000 unlk_a7.smt2 4e5f
counterexample for a7:
  a7 = #x00002000
  ccr = #x00
  spec #x00003000 flow #x00003004
CEX a7

    (-v prints every input register; the ones that are 0 are left out here.)

    A7 starts at 0x2000 and the long at 0x2000 is 0x3000. The specification gives A7 = 0x3000; the flow gives 0x3004.

    Why random testing missed it. The random test generator runs each candidate instruction on the reference model and keeps it only if the machine stays sane. One rule of sanity is that the stack pointer points into data memory, so an interrupt can always push a frame.

    UNLK A7 loads A7 from whatever long is in memory, which is almost never a sane stack address. The generator threw it away essentially every time. Compiled code never uses it either: compilers unlink with the frame pointer (UNLK A6), which was correct all along.

    The fix. Do the + 4 before the load, and load from -4(a7):

    add    a7, a7, x0       ; SP <- An
addi   a7, a7, 4        ; SP <- An + 4
ld.32  a7, -4(a7)       ; An <- (old An): the last write

    After the fix, with the same pins and with none:

    $ prove_pla -p a7=0x2000 -p m32@0x2000=0x3000 unlk_a7.smt2 4e5f
PROVED
$ prove_pla unlk_a7.smt2 4e5f
PROVED

    Bug 2: JSR (A7) and JSR d16(A7)¶

    The instruction. JSR <ea> pushes the return address and jumps to the effective address. With (A7) or d16(A7) the address is computed from the stack pointer, which the push itself changes.

    What the specification says.

    (defn jsr-ins (ins s)
  (if (jsr-addr-modep ins)
      (let ((s&addr (effec-addr (l) (s_mode ins) (s_rn ins) s)))
        (if (mc-haltp (car s&addr))
            (car s&addr)
          (jmp-mapping (cddr s&addr)
                       (push-sp (lsz)
                                (mc-pc (car s&addr))
                                (car s&addr)))))
    (halt (mode-signal) s)))

    The effective address comes first (effec-addr), from the state before the push. Then the return address is pushed (push-sp), and the jump goes to the address computed first. The target is therefore the old A7 (plus d16). The reference simulator agrees.

    The flow, before the fix. For JSR (A7) (opword 4E97):

    gpushr a7, 2            ; A7 <- A7 - 4; (A7) <- return address
gjr    a7, 0            ; jump to A7

    and for JSR d16(A7) (opword 4EAF):

    gpushr a7, 4
gjr    a7, {d16}

    The jump reads A7 after the push has moved it down by 4.

    The counterexample.

    $ prove_pla -v -p a7=0x2000 jsr_a7.smt2 4e97
counterexample for pc:
  a7 = #x00002000
  ccr = #x00
  spec #x00002000 flow #x00001ffc
CEX pc
$ prove_pla -v -p a7=0x2000 jsr_d16_a7.smt2 4eaf ffff
counterexample for pc:
  a7 = #x00002000
  ccr = #x00
  spec #x00001fff flow #x00001ffb
CEX pc

    The specification jumps to 0x2000; the flow jumps to 0x1ffc, into the return address it just pushed. With JSR -1(A7) (d16 = FFFF) the target should be 0x1fff; the flow again lands 4 bytes low. The indexed form JSR (d8,A7,Xn) was already right, because its address is computed into a temporary before the push.

    Why random testing missed it. The target of JSR (A7) has to be code, but A7 has to be a stack in data memory, and the generator keeps code and data apart. A program that jumps to its own stack pointer could not be generated, and no compiler produces one.

    The fix. For these two forms only, compute the target into a temporary first:

    add    x27, a7, x0      ; (addi x27, a7, d16 for d16(A7))
gpushr a7, 2
gjr    x27, 0

    Every other JSR keeps its two-uop flow.

    After the fix, all 132 comparable JSR and UNLK instances in the sweep prove, these included:

    $ prove_pla jsr_a7.smt2 4e97
PROVED
$ prove_pla jsr_d16_a7.smt2 4eaf ffff
PROVED

    On the core. Each bug now has a directed test that fails on the old core and passes on the fixed one:

    • the UNLK test stops when A7 disagrees with the reference by 4;
    • the JSR tests stop when the core retires an instruction at the target minus 4.

    The random generator now builds these forms on purpose:

    • MOVE.L A7,-(A7) + UNLK A7;
    • LINK A7,#0 + UNLK A7;
    • PEA (A7) / PEA d16(A7);
    • JSR (A7) / JSR d16(A7) into a routine in the code, with the return address pushed into junk words just before it.

    A copy of the core with each bug put back fails its directed test and every generated program.

    What a passing proof looks like¶

    ADD.L 16(A0),D1 (D2A8 0010): the flow loads the long at A0+16, adds it to D1 and sets X N Z V C.

    $ prove_pla add.smt2 d2a8 0010
PROVED

    That one line is a statement about every possible input: no value of A0, D1, the condition codes or the memory at A0+16 makes the flow and the specification differ in any register, flag, memory byte or the next pc.

    A proof with the multiply abstracted¶

    MULS.W (A0)+,D1 (C3D8): load a word, bump A0 by 2, and multiply 16 x 16 -> 32, signed.

    $ prove_pla muls.smt2 c3d8
PROVED abstracted: mul16s,mul32s

    SMT solvers are poor at showing that two different multiplier circuits compute the same product. Yu's specification multiplies the magnitudes and fixes the sign afterwards; the flow does one two's-complement multiply at another width. Without the abstraction, z3 did not finish this instruction in an hour, and Bitwuzla takes about a minute; with it, both take a fraction of a second.

    The abstraction gives both sides the same unnamed function mul16s(a, b) for "the 32-bit product of two 16-bit signed numbers". Before replacing a multiply, the prover proves that each operand really is a sign-extended 16-bit value. Then the solver only has to show that both sides apply the same function to the same operands.

    What it checks:

    • which bytes are loaded;
    • the address-register update;
    • that the operands are sign-extended, not zero-extended;
    • which register gets the product;
    • the flags;
    • the writeback.

    A flow that used MULU instead of MULS, or multiplied the wrong register, still fails. That was tested: the unsigned flow against the signed spec gives a counterexample.

    What it does not check is the multiplier itself: that mul16s really multiplies. Two things cover that instead:

    • The specification's sign-magnitude multiply is replaced by a two's-complement one in the lift. That replacement is checked against Yu's unmodified definitions, run concretely, on hundreds of random MULU/MULS/DIVU/DIVS instructions.
    • The core's multiplier is tested by the co-simulation.

    Divide is handled the same way (div32_16s, rem32_16u, ...). Every result that used the abstraction says so, so it is always visible which products and quotients were not checked bit for bit.
